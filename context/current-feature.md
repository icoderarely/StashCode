- **Dashboard UI Phase 1** — ShadCN UI init, dashboard route at /dashboard, dark mode by default, top bar with search and new item button (display only), placeholder sidebar/main areas.
- **Dashboard UI Phase 2** — Collapsible sidebar with top-level nav (Overview, All items, Favorites with counts), full 7-type "Item types" list linking to /items/TYPE, "Collections" section listing all collections, user avatar area, and an off-canvas drawer on mobile. Kept all 7 system types (incl. Image) despite the spec listing 6, confirmed with user.
- **Dashboard UI Phase 3** — Main content area: greeting header (mocked "current date" anchored to the mock data's timestamps), 4 stats cards (items/collections/favorite items/favorite collections), "Your collections" grid (dominant item-type icon/color per card), "All items" section with interactive filter tabs (All items, Favorites, Snippet, Prompt, Command, Note, Link) and item cards. Settings icon added to top bar. No dedicated "Pinned Items" section built, per spec note that it's not in the reference screenshot.
- **Prisma + Neon PostgreSQL** — Prisma 7.10.0 (pinned; `prisma@latest` resolves to an 8.0.0 RC) with the `prisma-client` generator emitting TypeScript to a gitignored `src/generated/prisma`. Connection URLs live in `prisma.config.ts` (v7 dropped auto env loading, so it imports dotenv); driver adapters are mandatory, so `@prisma/adapter-neon` runs on the pooled `DATABASE_URL` while the CLI migrates over the unpooled `DIRECT_URL`. Initial migration covers the core domain plus Auth.js models, with cascade deletes and FK indexes; seed inserts the 7 system item types. Added `db:*` scripts and `scripts/test-db.ts`. Known gap: `ItemType.@@unique([userId, name])` doesn't constrain system types since Postgres treats NULLs as distinct — seed works around it with `findFirst`; a partial unique index would need hand-written migration SQL. Nothing in the UI reads the DB yet; the dashboard still uses `src/lib/mock-data.ts`.
- **Seed Data** — Full demo dataset per `context/features/seed-spec.md`. Data is declarative in `prisma/seed-data.ts`; `prisma/seed.ts` writes it. Demo user `demo@devstash.io` / `12345678` (bcryptjs, 12 rounds — v3 ships its own types, so no `@types/bcryptjs`), 18 shared tags, 5 collections each with a `defaultTypeId`, 20 items (Snippet 4, Prompt 3, Command 5, Link 6, File 1, Image 1), 2 favorites, 2 pinned, 35 item↔tag links, no `Note` items since the spec lists none. Idempotent: the user is upserted by email, then that user's items/collections/tags are deleted and rebuilt (cascades clear the join tables), so re-runs don't stack duplicates. `file`/`image` items use placeholder `fileUrl`s until R2 is wired up; the image one points at placehold.co so the card renders. Deviations from the spec: type names stay capitalized (`Snippet`) to match the existing seed/UI, and React Patterns is marked a favorite collection so the dashboard's "favorite collections" stat isn't 0. 5 collections vs. the documented 3-collection free-tier cap is intentional per the spec. `scripts/test-db.ts` was extended to print the demo data (collections, every item with type/collections/tags/preview, favorite+pinned totals, per-tag usage) and assert the DB against `seed-data.ts` — counts, no untagged/uncollected items, no unused tags, contentType matching the populated field — exiting 1 with "Run: npm run db:seed" on mismatch. No schema change, so no migration. The dashboard still reads `src/lib/mock-data.ts`.
- **Dashboard Collections** — First DB-backed UI, per `context/features/dashboard-collections-spec.md`. `src/lib/db/collections.ts` exposes `getRecentCollections(userId)`: `where: { userId }`, `updatedAt desc`, `take: 6`, pulling `_count.items` plus each item's `createdAt` and `itemType` in one query, then deriving the dominant type and the distinct-type list in TS rather than with a second `groupBy`. Tie-break is `defaultTypeId` when it's one of the tied types, else the tied type with the earliest item — the seed never hits it (every collection has a clear winner), so it's untested against real data. `await connection()` sits in front of the query so the route isn't prerendered at build; `/dashboard` is now `ƒ (Dynamic)` and the build no longer needs a reachable database. Return shapes live in `src/types/collection.ts`. Auth.js isn't wired up yet, so `src/lib/db/user.ts` has a placeholder `getCurrentUserId()` that looks up `demo@devstash.io` by email and returns null if it's missing — replace it with the session lookup when auth lands. `CollectionsSection` became an async server component (no client fetch, no loading state this pass) and gained an empty state; `CollectionCard` now takes a `RecentCollection` and tints via `color-mix(in oklab, <type> 10%, var(--card))` for background and `30%, transparent` for border, which composites correctly over `--card` in a way a flat `#rrggbbaa` wouldn't. Deviations: the screenshot's single large icon badge became a row of size-7 type chips (dominant first, capped at 5 + `+N`) because the spec asks for one icon per distinct type; the grid stays `lg:grid-cols-5` to match the screenshot, so a 6th collection would wrap to its own row. Item chips inside cards are out of scope per the spec. The sidebar collections list and the stats cards still read `src/lib/mock-data.ts`, which leaves `src/lib/collection-utils.ts` (mock-only `getDominantItemType`) dead code — kept pending a decision. No schema change, so no migration. Pre-existing and unrelated: the TopBar `<Input>` logs a hydration mismatch in dev.
- **Dashboard Items** — Per `context/features/dashboard-items-spec.md`, the rest of the dashboard's main area moved onto the database. `src/lib/db/items.ts` has `getRecentItems(userId)` (`updatedAt desc`, `take: 6`) and `getPinnedItems(userId)` (`isPinned: true`, no limit), sharing one `DASHBOARD_ITEM_SELECT` that pulls `itemType` plus — via `take: 1, orderBy: { addedAt: "asc" }` on the join table — only the single owning collection the card labels itself with, rather than every membership. `src/lib/db/stats.ts` has `getDashboardStats(userId)`: four `count`s in a `Promise.all`; it lives on its own because the row spans items *and* collections. Shapes in `src/types/item.ts` and `src/types/stats.ts`. `CollectionItemType` was really an item-type summary, so it moved to `item.ts` as `ItemTypeSummary` and `src/types/collection.ts` imports it — no behavior change, just a name that isn't a lie. `getCurrentUserId()` is now wrapped in React `cache()`: four sections resolve the user independently and without it that's four identical queries per request. `ItemsSection` flipped from client to async server (header + fetch); the tabs and grid moved to a new client `ItemsBrowser`, which is the "server parent passes props down" split the spec asked for. New `PinnedItemsSection` returns `null` when nothing is pinned — no heading, no empty state — and sits between collections and "All items" (the screenshot has no pinned section to copy). `ItemCard` gained the 3px type-colored left border from design.md and a pin indicator, and now reads type/description/collection off the query. `StatsCards` is async and fully DB-backed; doing only the collection halves would have put real and mock numbers side by side in one row. One forced change outside items: `formatRelativeTime` defaulted `now` to `MOCK_NOW` (2024-09-24), which is *behind* real seeded rows, so every real item rendered "Just now" — it now defaults to the real clock and takes `Date | string`. Because `ItemCard` renders server-side under `PinnedItemsSection` but client-side under `ItemsBrowser`, `now` is computed on the server and threaded down as a prop so both passes format identically; without it a card near a boundary ("59 min ago" vs "1 hour ago") could hydrate differently. Verified against the seed: stats 20/5/2/1, exactly the 2 seeded pinned items, 6 recent cards with correct type colors and collection names, times reading "3 days ago", no dev-log errors. Left alone deliberately: the "All items" badge still counts the 6 fetched items rather than all 20 (unchanged behavior, "View all" sits next to it); `DashboardHeader` and `Sidebar` are the last `mock-data` consumers, so the header still reads "September 24, 2024" / "Good morning, Jordan" while the cards below say "3 days ago" — both are user/greeting concerns for the auth pass, but the inconsistency is now visible. `src/lib/collection-utils.ts` is still dead code. No schema change, so no migration.
